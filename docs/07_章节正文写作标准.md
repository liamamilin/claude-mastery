# 07｜一章能教会人，而不是一章写满术语

## 单章结构（建议顺序，可因内容调整）

1. **先给真实任务**：读者本章需要解决什么困境；不要先写一页广告。
2. **完成之后能做到什么**：一两句可观察的结果。
3. **准备状态**：在哪个界面，打开哪个目录，用哪个案例，默认模式/文件是什么。
4. **做第一次尝试**：逐步交代“你点击/输入什么；Claude 可能做什么；你如何确认”。
5. **为什么这么做**：穿插解释概念（最多引入本章必要概念），避免孤立术语表。
6. **观察结果与反例**：明确看实际文件、页面、diff、测试，不以 Claude 声称完成为准。
7. **失败时怎么办**：写至少一种具体失败状态及调整方式。
8. **独立练习**：改变一个条件，不给全部操作，让读者迁移能力。
9. **掌握检查**：两到三问，不是背术语。明确下一章连接。
10. **事实注记**：本章使用到的 CLI/按钮/权限/模型与官方链接和核查日期。

## 章节的长度与密度

用“读者能完成一个有意义的行动”确定长度，不能用统一字数约束拖慢写书；拒绝大段抽象建议。能图解的复杂关系用精确 SVG，步骤细节用真实截图，示例输出区分实际日志与示意文本。

## 提示词写法

永远明确发送位置。例如：

> **发送到 [Desktop Code] 提示框**：请先查看项目目录，告诉我现有代码如何保存收藏，暂不修改文件。把你看到的文件与理由列出来。

不是终端命令的文字不要包成 `sh` 代码块，更不要让读者复制普通自然语言进 shell。对可复制提示词，用独立区块，解释是否允许 Claude 自主改文件。

### 不允许的写法

- “输入 `/init` 就自动获得完美工程规范”；须说明是对现状的初始化建议，需审阅内容。
- “Claude 自己会知道我想做什么”；必须教会提供目标和上下文。
- “测试通过所以完全没问题”；描述覆盖范围和未验证边界。
- “本章已经涵盖所有权限风险”；只说与当前操作有关的事实和控制方式。
- 大量编造 Claude 的逐字回答当成“实际运行记录”。

## 初学者路径的低门槛

- 首次出现 `localhost`：说明这是当前电脑用于访问本地应用的地址，正式网站仍可用 GitHub Pages。
- 首次出现 `git diff`：说明它是显示修改前后的差异，允许先在图形面板查看。
- 首次出现 `npm`：说明用于安装/运行 Node 项目所需工具，并提供 Node 安装/检查步骤。
- 首次出现 `worktree`：用“一份项目的另一处独立工作目录”解释，再进细节。

## 出版与截图风格

每章至少一个清晰的视觉或代码观察点；但不得为凑图而插不相关图片。截图带平台与日期版本，不泄露机密。

## 样稿索引

- `book/chapters/22-停止反复补丁.md`：行为证据、根因诊断与反复修补。

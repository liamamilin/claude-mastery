# 第 05 章｜需求不清楚，如何带 Claude 一起探索

> 本章终点：面对一句模糊的想法（“我想更方便收藏资料”），你能让 Claude 先给出**三个可比较的小方向**，自己挑一个，并要求它只做一个**最小样板**。你能清楚地区分“探索”和“实施”两种指令。

## 1. 一句话的两种结局

> “我想更方便地收藏资料。”

如果你把这句话原样发给 Claude 并允许它直接动手，通常会发生两种事之一：

- **它猜一个方向，做得很大。** 你得到一个带账号、标签、云同步的“系统”，而你只想记几个网址。
- **它反问一堆问题。** 你被迫回答“用什么技术栈？”“要不要登录？”，这些问题你也不知道。

两种结局的共同问题是：**探索被当成了实施。** 你还不知道要什么的时候，最有价值的产物不是代码，而是**几个可以比较的选项**。

## 2. 两种模式的区别

| | 探索 | 实施 |
|---|---|---|
| 你说的话 | “给我几个方向，不要改文件” | “做这个，范围是…” |
| Claude 的产出 | 选项、取舍、问题 | 文件、diff、可运行结果 |
| 失败的代价 | 几乎为零 | 可能要回退 |
| 你的角色 | 比较与选择 | 核对证据 |

Desktop 的权限模式正好服务于这种区分：**Plan** 模式让 Claude 探索并提出计划，而**不修改源代码**（官方参考：Plan 仅作用于当前会话）。不过探索并不只能在 Plan 模式里做——在 Manual 模式下你同样可以用一句“暂时不要修改任何文件”来约束它。选哪个，第 08 章再系统讨论。

## 3. 动手：把“更方便收藏资料”变成三个方向

**准备**：打开你在第 4 章复制的 `lab-a` 练习目录，新建一个 Local 会话。模式用 **Plan**，或 Manual 并明确禁止改文件。

**发送到 [Desktop Code] 的提示框（探索，不改文件）：**

> 我有一个收藏链接的小工具（就在当前目录，请先看一下现有文件）。我想让它“更方便收藏资料”，但我还说不清具体要什么。
>
> 请不要改任何文件。基于现有代码，给我三个**互相有区别**的小改进方向。每个方向写清楚：
> 1. 它解决什么具体的不方便；
> 2. 大概要改哪些文件、会不会破坏现有的保存行为；
> 3. 我怎么在浏览器里一眼看出它做成了。
>
> 最后告诉我，如果只做一个，你推荐哪个，为什么。

这段话里有几处刻意的设计：

- **“先看一下现有文件”**：让方案建立在真实代码上，而不是空想。
- **“互相有区别”**：避免得到三个只是措辞不同的同一个方案。
- **“怎么一眼看出做成了”**：把方案和第 06 章的“可观察行为”提前连接起来。
- **“推荐哪个”**：要它做判断，但选择权在你。

### 你可能看到什么（示意，不是实际输出）

不同的会话、不同的模型版本，回答会不同。下面只是**示意**，展示你应该拿到的“形状”：

| 方向 | 解决的不方便 | 影响范围 | 验证 |
|---|---|---|---|
| A 搜索框 | 收藏变多后找不到 | `index.html` + `app.js`，不改存储格式 | 输入关键词，列表实时过滤 |
| B 标签 | 无法分类 | 数据结构新增字段，旧数据需要兼容 | 添加带标签的条目，按标签筛选 |
| C 导出 JSON | 怕浏览器数据丢失 | 新增一个按钮与下载逻辑 | 点击后得到文件，内容是收藏列表 |

**你的任务是评估，不是接受。** 一个值得问的问题是：哪个方向会**改变已有数据的格式**？格式一旦改变，旧收藏就有可能读不出来——这是风险最高的那个。

## 4. 比较和选择

给自己三个判断标准：

1. **小**：能不能在一个会话里完成并验证？
2. **可见**：做成之后，你能不能亲眼看到？
3. **安全**：会不会破坏现有的功能？

假设你选了 A（搜索框）：它小、可见、不改存储格式。

## 5. 从探索切到实施：只做样板

**发送到 [Desktop Code] 的提示框（允许改文件）：**

> 我选方向 A。请只做一个最小版本：在列表上方加一个输入框，按标题实时过滤，不区分大小写。不要改变保存数据的方式，不要加别的功能。完成后告诉我，我应该在浏览器里按什么步骤验证。

注意**范围的声明**：“只做最小版本”“不改保存方式”“不加别的功能”。它们是第 3 章里 diff 检查的依据——你可以用它们判断 Claude 有没有越界。

做完后用第 4 章的三种证据核对。**不通过也很正常**，这是本书后续章节的来源。

## 6. 失败分支：它拒绝只给选项

有时 Claude 会在你只想要选项时直接动手改文件。

- 在 Manual 模式下：**拒绝**那次变更，并说明“我这一轮只要方案，不要改文件”。
- 若你使用 Plan 模式：它本来就不会改源代码，这是选用 Plan 的原因之一。

另一种失败是：三个方向实际上是同一个方案的变体。回应方式：

> 这三个方向太相似了。请给出一个**改变数据格式**的、一个**不改任何 UI** 的，和一个**最小**的方向，各自说明取舍。

## 7. 独立练习

把下面这句模糊需求换成你自己真实的、小的想法，重复本章的流程：

> “我想让 LinkShelf 更适合手机使用。”

要求：先要三个方向 → 写下你选择的理由（至少两句话）→ 只做一个最小样板。

## 8. 掌握检查

1. 为什么“探索”阶段的好产物不是代码？
2. 提示里要求“怎么一眼看出做成了”，对后面哪个步骤有帮助？
3. 三个方向里哪一个最危险，为什么？

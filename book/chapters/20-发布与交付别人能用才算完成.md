# 第 20 章｜发布与交付：别人能用才算完成

> 本章终点：你能用一份**交付检查单**判断一个静态网站是否真正可以交给别人使用；你理解 GitHub Pages 的“项目页”为什么需要 `base`，并亲自在本地用子路径构建验证；你知道哪些发布动作需要你亲自授权。

## 1. “在我电脑上能跑”不是交付

前面每一章，你的验证都发生在自己的电脑上。但“完成”的含义是：**一个没有你在场的人，也能打开并使用它。**

对静态网站，这至少包括：

- 它**在发布后的真实地址**能打开；
- 页面里的资源（图片、样式、脚本、链接）**路径在子路径下也正确**；
- 它**不依赖你电脑上才有的东西**（本地服务、你的目录、未提交的文件）；
- 别人能**从零构建**出同样的结果。

## 2. 为什么 GitHub Pages 的项目页需要 `base`

GitHub Pages 有两种常见地址：

| 类型 | 地址 | 站点根路径 |
|---|---|---|
| 用户页 | `https://<用户>.github.io/` | `/` |
| 项目页 | `https://<用户>.github.io/<仓库名>/` | `/<仓库名>/` |

本书的站点会作为**项目页**发布。如果构建时仍然把资源写成 `/assets/app.js`（以根路径开头），浏览器会去 `https://<用户>.github.io/assets/app.js`，而它实际在 `https://<用户>.github.io/<仓库名>/assets/app.js`——**404**。

VitePress 用配置项 `base` 解决这个问题。本项目的 `book/.vitepress/config.mts` 会自动决定它：优先读取环境变量 `SITE_BASE`，其次根据 GitHub Actions 提供的 `GITHUB_REPOSITORY`（形如 `用户/仓库`）推导，用户页仓库（名字为 `<用户>.github.io`）用 `/`，其余用 `/<仓库名>/`。

> 名词：**CI / GitHub Actions** 是 GitHub 的自动化流程，可以在你推送代码后自动构建、发布。本项目的 `.github/workflows/deploy.yml` 就是这样的流程。

## 3. 动手：在本地验证子路径构建

这一步**不需要联网、不需要推送**。在本书项目根目录：

```sh
SITE_BASE=/claude-mastery/ npm run build
```

然后检查产物里的资源路径：

```sh
grep -o 'src="[^"]*app[^"]*"' book/.vitepress/dist/index.html | head -1
```

作者实测输出形如 `src="/claude-mastery/assets/app.XXXX.js"`（哈希部分每次不同）——**带上了子路径**。

再模拟 GitHub Actions 的方式（它会设置 `GITHUB_REPOSITORY`）：

```sh
GITHUB_REPOSITORY=liamamilin/claude-mastery npm run build
```

作者实测：同样产出 `/claude-mastery/assets/...`。而把变量换成用户页仓库 `liamamilin/liamamilin.github.io` 时，产出 `/assets/...`（根路径）。**两个分支都符合预期。**

### 在子路径下真正打开一次

构建通过不代表页面能用。启动预览：

```sh
SITE_BASE=/claude-mastery/ npx vitepress preview book --host 127.0.0.1 --port 48124
```

打开 `http://127.0.0.1:48124/claude-mastery/`（注意末尾的子路径）。作者实测：首页和章节页返回 200，章节里的 SVG 图片能加载。

> 如果你的 48124 端口已被占用，换一个。预览结束后在终端按 `Ctrl+C`。

### 一个常见陷阱：手写路径

Markdown 里的图片 `![…](/figures/x.svg)`，VitePress 会自动补上 `base`。但在 Vue 组件或手写 HTML 里写 `src="/figures/x.svg"`，**不会**自动补——要用 `withBase('/figures/x.svg')`。本书的组件已经这样处理（作者检查过 `LandingHero.vue` 与 `MasteryLoop.vue`）。

## 4. 用 `npm ci` 验证“从零构建”

`npm install` 会根据情况更新依赖；`npm ci` 严格按 `package-lock.json` 从零安装，更适合在自动流程里使用。本项目的工作流用的是 `npm ci`。作者在一个只含 `package.json` 与 `package-lock.json` 的全新目录里实测：`npm ci` 成功，构建通过。

这就回答了“别人能不能从零构建”：**可以，前提是锁文件已经提交。**

## 5. 交付检查单

发布前，逐项打勾：

| 类别 | 检查 | 方法 |
|---|---|---|
| 构建 | 从零构建成功 | `npm ci && npm run build` |
| 路径 | 子路径下资源都能加载 | 带 `SITE_BASE` 构建并预览 |
| 内容 | 没有占位文字、没有“待编写”的入口被当成已发布 | 通读导航与首页 |
| 链接 | 站内链接没有 404 | 点一遍；VitePress 构建会检查死链 |
| 手机 | 375px 宽度没有横向滚动 | 第 17 章的方法 |
| 隐私 | 没有密钥、账号、个人路径 | 搜索 `token`、`password`、你的用户名、家目录 |
| 版本 | 有说明“核对日期”，易变信息已标注 | 看每章的事实注记 |
| 回退 | 知道怎样回到上一个能用的版本 | Git 提交与标签（第 15 章） |

## 6. 哪些发布动作需要你亲自决定

| 动作 | 为什么要你来决定 |
|---|---|
| 创建公开仓库 | 内容立刻对外可见 |
| `git push` 到远程 | 把你本地的内容送到别人的服务器 |
| 开启 GitHub Pages 并触发工作流 | 站点出现在公开互联网 |
| 绑定自定义域名、购买服务 | 涉及账号、费用 |

这些动作**一旦做了，内容可能已被缓存或索引，即使之后删除也难以完全撤回。** 因此即便你把仓库地址给了 Claude，也应当在它推送之前**明确说“可以推送”**。链接本身不是授权。

## 7. 失败分支：发布后样式丢失

页面打开了，但没有样式、图片全裂开：

1. 打开浏览器的网络面板，找一个 404 的资源，看它请求的路径；
2. 路径缺少 `/<仓库名>/`？→ `base` 没生效。检查 `SITE_BASE`/`GITHUB_REPOSITORY`，或手写路径没用 `withBase`；
3. 路径对，但仍 404？→ 产物没有上传，或工作流用的目录不对（本项目是 `book/.vitepress/dist`）；
4. 只有最新内容没更新？→ 浏览器缓存，或工作流失败了没发布，看 Actions 的运行记录。

**先看一个真实的 404 请求，再决定怎么修**——这是第 22 章“找证据再动手”的同一原则。

# 第 10 章｜用附件、@文件、截图和日志给足证据

> 本章终点：对同一个故障，你分别用“只描述”“加截图”“加精确证据”三种材料请 Claude 调查，并**记录哪一种材料带来了关键差异**。你学会选材料，而不是堆材料。

## 1. 一份典型的坏报告

> “任务看板坏了，一个任务都没有了。”

这句话描述了现象，但把所有调查工作都留给了 Claude：是服务没启动？数据文件丢了？代码出错？浏览器缓存？它只能逐个猜，而且它还可能开始改代码来“修复”。

给证据的目的，是让它**少猜、多查**。

## 2. 复现故障（真实的）

资料包里的 Lab B 附带一个故障场景：`scenarios/trailing-comma/issues.json`。这是一份数据文件，**末尾多了一个逗号**——人手工编辑 JSON 时常见的笔误。

1. **[系统文件管理器]** 复制 `lab-b-issueboard` 为 `lab-b3`。
2. 用 `scenarios/trailing-comma/issues.json` **覆盖** `lab-b3/data/issues.json`。
3. 在 `lab-b3` 里启动静态服务（第 9 章的命令，换一个空闲端口）。
4. 在 Browser 窗格打开页面。

### 你会看到

作者在 2026-10-26 的实测：页面显示 **“共 0 个任务，未完成 0 个”**，三列都是空的，**没有任何错误提示**。

## 3. 收集证据：三类材料

在发给 Claude 之前，自己先收集下面三样，看看哪一样信息量最大。

### 材料 A：现象截图

页面截图显示“共 0 个任务”。它说明**症状**，但不说明原因。

- 在 Desktop 里，可以通过提示框的 **+** 按钮添加附件，或直接拖拽图片进提示框（官方说明支持图片、PDF 等）。
- 截图前注意：别把你的账号、通知、其他窗口截进去。

### 材料 B：请求记录

在 Browser 窗格的开发者工具（或普通浏览器开发者工具）的网络面板里查看对 `data/issues.json` 的请求。作者实测：**状态码是 `200 OK`**。

这是一条**排除性证据**：文件取到了，不是 404，不是服务没启动，不是路径写错。

### 材料 C：解析错误

文件取到了却没有显示，下一个合理假设是“内容读不出来”。在页面的控制台执行：

```js
JSON.parse(await (await fetch('data/issues.json')).text())
```

作者实测得到：

```text
SyntaxError: Unexpected token ']', ..."小周"},
]
" is not valid JSON
```

> 具体措辞因浏览器而不同（这是在 Browser 窗格内置浏览器中的结果）。重点是它**直接指出了位置**：`]` 之前多了逗号。

## 4. 三轮对比实验

每一轮都用 **新会话**（避免上下文污染），权限模式 **Plan**，目标目录 `lab-b3`。

**第一轮：只有描述**

> 页面显示“共 0 个任务”，应该有 5 个。请找出原因，先不要改文件。

**第二轮：描述 + 截图（A）**

把截图拖进提示框，再发：

> 附图是现象。应该有 5 个任务。请找出原因，先不要改文件。

**第三轮：描述 + B + C，并 @ 相关文件**

> 页面显示“共 0 个任务”。网络面板里 `data/issues.json` 返回 200 OK。在控制台手动 JSON.parse 该文件报错：`SyntaxError: Unexpected token ']'`（位置在 "小周"}, 之后）。请先看 @data/issues.json 和 @src/main.js，告诉我：原因是什么？为什么页面没有显示任何错误提示？先不要改文件。

## 5. 一个值得注意的发现：第二个问题

第三轮的第二个问题——“为什么页面没有显示任何错误提示？”——不是随口问的。

读 `src/main.js` 会发现：`load()` 在出错时确实往 `#summary` 写了错误提示，但随后 `load().then(render)` 调用 `render([])`，**立刻用“共 0 个任务”覆盖了它**。所以：

1. **根因**：数据文件有语法错误；
2. **次生缺陷**：错误提示被覆盖，用户看不见。

只修数据（根因）后页面恢复；但下一次别的原因再导致加载失败，用户仍然看不到提示。**一个有经验的修复会同时处理两层。**

这个次生缺陷是作者实测中**真实发现**的，并非预先埋入。它说明：给足证据，你不仅更快找到问题，还能发现“系统为什么没有告诉你”。

## 6. 什么材料不该给

| 不该给 | 原因 |
|---|---|
| 整个仓库的文件列表与所有源代码 | 淹没关键线索，占用上下文 |
| 几百行不相关日志 | 同上；挑出与故障时间点相关的几行 |
| 含密码、令牌、个人信息的文件 | 隐私；先脱敏 |
| “我觉得是 X 的问题”的猜测，当成事实 | 会把 Claude 带偏；若要给，明确标注为猜测 |

材料质量的判断标准：**它能不能让某个假设被排除或证实？** 能，就留；不能，就删。

## 7. 失败分支：证据给了，Claude 仍然走偏

假设第三轮里 Claude 仍然提议“重写 `fetch` 逻辑”。

不要继续补充更多材料。先问：

> 你的假设是什么？它与“200 OK 且 JSON.parse 报错”这两条证据怎样兼容？

如果它无法解释，让它对照证据逐条重新推理。这是第 22 章“检查隐含假设”的预演。

## 8. 修复（可选）

做完对比实验后，用第三轮的会话切到 Manual，发送：

**验证（两项都要做）：**

# 第 13 章｜权限模式：怎样设置合适的自主性

> 本章终点：你能为四种不同风险的任务各选一个权限模式并说出理由；你亲眼比较过 **Manual** 与 **Accept edits** 在同一任务上带来的审批差异；你知道哪两个模式需要额外谨慎，以及为什么“更自动”不等于“更好”。

## 1. 自主权是一个旋钮，不是开关

第 2 章你选了 Manual，第 8 章你用了 Plan。现在把这排选项放在一起看——它们实际上是**你把多少判断权交给 Claude**的刻度：

| 界面名称（设置键） | 它做什么 | 你承担什么 |
|---|---|---|
| **Plan**（`plan`） | 只探索、提出计划，不改源代码。仅当前会话有效 | 几乎没有风险 |
| **Manual**（`default`） | 改文件、运行命令前都问你 | 逐项审阅，容易疲劳 |
| **Accept edits**（`acceptEdits`） | 自动接受文件编辑和常见文件系统命令（如 `mkdir`、`touch`、`mv`）；其他终端命令仍询问 | 要靠事后 diff 发现问题 |
| **Auto**（`auto`） | 不做常规询问，由后台分类器在命令和网络请求执行前检查它们是否符合你的请求，拦截有风险的 | 信任分类器；分类器不是万能 |
| **Bypass permissions**（`bypassPermissions`） | 几乎没有提示，只保留少数无法自动批准的动作 | 全部风险；官方建议只在沙箱容器或虚拟机里用 |

> 来源：官方 [Desktop 参考](https://code.claude.com/docs/en/desktop)，2026-10-26。早期版本的标签叫 Ask permissions / Auto accept edits / Plan mode。

几个事实要记住：

- 你在选择器里选的模式会**按文件夹被记住**，并覆盖设置文件里的默认值（`permissions.defaultMode`），**Plan 除外**——它只对当前会话生效。
- **Auto** 需要受支持的模型（官方列出 Opus 4.6 及以上、Sonnet 4.6 及以上、Haiku 5.5，或 Fable 系列），管理员可以关闭它。你看不到这个选项，可能是模型或组织策略的原因。
- **Bypass permissions** 在 Pro 和 Max 上需要先在 **Settings > Claude Code** 打开 **Allow bypass permissions mode**；Team 与 Enterprise 没有这个开关；云端会话不提供。官方明确说它等价于命令行的 `--dangerously-skip-permissions`。**本书不推荐在你的日常电脑上使用它。**

## 2. 选择自主性的三个因素

选模式不看“我信不信 Claude”，而看**出错的代价**和**你能多快发现**：

1. **可逆性**：改动能不能轻松撤回？（有 Git 提交吗？）第 15 章会让这件事变得具体。
2. **影响范围**：只动练习目录，还是会碰到你电脑上别的东西？命令会不会联网、安装软件、删除文件？
3. **可见性**：事后你能不能通过 diff、测试或页面一眼看出问题？

三个都好 → 可以更自动；任何一个差 → 回到 Manual 甚至 Plan。

## 3. 动手：同一个任务，两种模式

准备两份干净的 Lab A 副本：`lab-a-m` 与 `lab-a-e`。两个会话都选 Local。

**任务（两个会话发送同样的话）：**

> 请把页面标题和主标题改成“我的收藏架”，并在项目里新建一个 `notes` 文件夹，在里面放一个 `todo.md`，写一行“后续：加搜索”。

- 会话一：**Manual**。
- 会话二：**Accept edits**。

### 观察并记录

| 观察项 | Manual | Accept edits |
|---|---|---|
| 新建 `notes` 文件夹是否需要你批准？ | | |
| 修改 `index.html` 是否需要你批准？ | | |
| 完成后你是通过什么发现改了哪些东西？ | | |

官方描述的预期：Accept edits 会自动接受文件编辑和 `mkdir`、`touch`、`mv` 这类常见文件系统命令。**以你实际看到的为准**——不同版本的细分可能有变化，你的记录才是结论。

### 然后问自己

- 在 Accept edits 下，如果 Claude 同时改了你没要求的文件，你是在**事前**还是**事后**发现的？
- 两种模式各自适合这个任务吗？这个任务可逆、范围小、可见——答案可能是“都适合，Accept edits 更省事”。换一个任务呢？

## 4. 四个任务，选四个模式

先自己选，再看参考。

**任务 A**：修一个错别字（改一行文字）。
**任务 B**：第一次接手陌生项目，要它先摸清结构。
**任务 C**：在一个**没有提交过**的、含有你唯一副本的真实作品上做重构。
**任务 D**：要它安装一个你没听说过的依赖并运行其脚本。

### 参考思路

- **A：Accept edits（甚至 Manual 也行）**。改动小、可见、可逆。
- **B：Plan**。只读调查，不需要任何写权限（第 9 章）。
- **C：先不要动手。** 先做一份提交（第 15 章）让它可逆；在此之前用 Manual，或直接先停下来。**不可逆的前提下，不管哪个模式都过早。**
- **D：Manual，并且逐条阅读命令。** 安装并运行陌生脚本，就是官方为 Bypass 和 Auto 列出风险的那一类行为：联网、执行未知代码。不要让“节省点击”压过判断。

## 5. 一个不对称：自动模式不会替你设范围

即使在 Auto 下，Claude 仍然会按**你的请求**行动。很多事故不是模式选错，而是请求没有划边界：

> “把项目清理一下。”

在 Manual 下，你会在批准界面看到“删除某某文件”，有机会拒绝。在更自动的模式下，这个判断需要提前写进任务说明（第 7 章：硬约束放在明显位置）：

> “清理 `lab-a` 目录里多余的文件。**只列出建议删除的文件，不要删除任何东西。**”

> 如果你想让某些行为**无论如何**被阻止，不要依赖提示词。官方的做法是权限规则或 hook（第 27 章）；CLAUDE.md 里的话只是上下文，不是强制。

## 6. 失败分支：批准疲劳

Manual 下连续批准十几次后，你开始不看内容就点“接受”。这是官方最佳实践里点名的现象：**点着点着，你不是在审阅，而是在点击。**

解决方式不是“再努力一点”，而是**改变结构**：

1. 把任务拆小，每次改动少；
2. 把只读调查放到 Plan 里；
3. 对安全且重复的改动切到 Accept edits，**把审阅点移到 diff**；
4. 对高风险步骤，保留 Manual。

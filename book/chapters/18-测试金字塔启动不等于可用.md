# 第 18 章｜测试金字塔：启动不等于可用

> 本章终点：你能说出三层检查——**逻辑测试、页面行为检查、真实使用验收**——各自能发现什么、发现不了什么；你亲眼看到一个“测试通过、页面却坏了”的真实例子；你为一项功能写出覆盖三层的最小验收。

## 1. “测试通过”这句话的空白

Claude 汇报：“我运行了测试，全部通过。”这可能是真的，也可能毫无意义。区别在于：**这些测试检查了什么？**

官方最佳实践把这类现象命名为“信任—验证缺口”：Claude 给出看起来合理的实现，却没有处理边界情况，而你以为已经验证了。对策是：**始终提供验证（测试、脚本、截图）；如果你无法验证，就不要发布。**

## 2. 三层检查

| 层 | 检查什么 | 速度 | 能发现 | 发现不了 |
|---|---|---|---|---|
| **逻辑测试** | 纯函数的输入输出 | 毫秒级 | 计算、分组、过滤规则错误 | 页面是否显示、点击是否响应 |
| **页面行为检查** | 浏览器里运行页面、操作、读结果 | 秒级 | 数据加载、事件、错误提示、布局 | 你没设想到的使用方式 |
| **真实使用验收** | 你亲自像用户那样用 | 分钟级 | 好不好用、对不对味 | 只覆盖你试过的路径 |

底层越多、越便宜、越快；上层越少、越贵、越接近真实。叫“金字塔”，是因为**健康的组合是底层多、上层少，而不是只靠其中一层。**

## 3. 真实例子：Lab B 的测试通过了，页面仍然会坏

第 10 章你复现过 Lab B 的 trailing-comma 故障，页面显示“共 0 个任务”且没有提示。现在看这件事与测试的关系。

**逻辑测试（`node test.mjs`）：**

- 在正常数据上：`PASS Lab B baseline: grouping, open count, one legacy issue without priority`；
- 作者把 `data/issues.json` 换成 trailing-comma 版本再运行，测试**直接崩溃**，输出以 `SyntaxError` 开头。

所以这个测试**会**发现数据文件语法错误——算是一个收获。

**但它发现不了：**

- `main.js` 在加载失败时的错误提示被 `render([])` 覆盖——测试根本没加载 `main.js`；
- 页面最终显示的是什么。

这个缺陷只在**页面行为检查**那一层可见。换句话说：**对同一个项目，一层通过不能替另一层作证。**

## 4. 动手：给 Lab B 的新功能写三层验收

回到第 12 章中做到一半的“优先级过滤”。完整的三层验收如下。

### 第一层：逻辑测试

目标：`filterByPriority(issues, level)`。

在 `test.mjs` 末尾加（示意，由 Claude 实现函数后运行）：

```js
// 选“高”只有 id 1 和 5
assert.deepEqual(filterByPriority(issues, 'high').map(i => i.id), [1, 5]);
// 没有 priority 字段的 id 4，归入“普通”
assert.ok(filterByPriority(issues, 'normal').some(i => i.id === 4));
// “全部”不过滤
assert.equal(filterByPriority(issues, 'all').length, 5);
```

> 这里的三条断言正好对应第 6 章的完成条件。**先写验收，再让 Claude 实现，反过来会让它“照着现状写测试”。**

提示 Claude：

> 请在 `test.mjs` 中增加上面三条断言（我已写好），再在 `src/board.js` 实现 `filterByPriority` 让它们通过。**不要修改我写的断言。** 运行 `node test.mjs` 并告诉我输出。

“不要修改断言”这句话很重要：有的实现会通过改测试来“通过测试”。看 diff，确认 `test.mjs` 里你的三条没变。

### 第二层：页面行为检查

逻辑通过之后，页面接线（下拉框与渲染）仍可能出错。在 Browser 窗格里：

| 动作 | 应看到 |
|---|---|
| 初始 | “共 5 个任务，未完成 4 个” |
| 选“高” | 只显示 2 个任务（id 1、5） |
| 选“全部” | 5 个 |
| 把数据换成 trailing-comma 版本再加载 | **应显示加载失败提示**，而不是“共 0 个任务” |

最后一项把第 10 章的次生缺陷变成验收条件。

### 第三层：真实使用验收

你亲自做：

- 随意切换几次过滤，有没有明显卡顿或闪烁？
- 对不熟悉这个看板的人，“高/普通/低”的措辞是否一看就懂？

这一层机器做不了。

## 5. 常见的“假绿”

“假绿”指测试通过但并没有证明什么：

| 假绿 | 识别方法 |
|---|---|
| 测试里没有断言，或断言永真 | 故意把实现改坏，看测试是否变红 |
| 测试是 Claude 照着自己的实现写的 | 看是否有一条来自**你**的验收条件 |
| 只测了“正常路径” | 问：空数据、缺字段、非法输入怎么办？ |
| 测试跑的是旧代码 | 在测试里故意加一个失败断言，确认它真的会运行 |

**让测试先红再绿**是一个很实用的习惯：先确认它在功能缺失时会失败，实现后再变成通过。

## 6. 失败分支：测试通过，但验收不通过

遇到这种情况，不要说“代码没问题，测试都过了”。把它当作一个信息：**测试没有覆盖这条验收**。做两件事：

1. 把这条验收补进测试或页面检查，让它能变红；
2. 修复使它变绿。

这样同一个问题不会第二次溜过去。

## 7. 独立练习

为 Lab A 的“搜索功能”（第 6 章的清单）设计三层验收：每层各写两条，指出每一条的**失败时会看到什么**。再想想：哪一条最容易被忽略？为什么？

# 第 23 章｜桌面环境问题与工具连接故障

> 本章终点：遇到“命令找不到”“端口被占用”“预览打不开”“工具没连上”这类问题时，你不是让 Claude 到处试，而是**先看版本、再看日志、最后看具体症状**；你至少亲手排查过两个真实的环境故障。

## 1. 环境问题的特点

环境问题和代码问题不同：

- **代码没有错**。同一份代码在别的电脑上完全正常；
- **症状常常误导**。“页面打不开”可能是服务没启动，也可能是端口被占，也可能是网址写错；
- **Claude 很容易越修越乱**。因为它不一定知道你电脑上装了什么。如果它开始安装东西、改系统设置，请立即停下来。

所以本章的原则是：**先问“是什么”，再问“怎么办”。**

## 2. 先看三样：版本、日志、症状

| 先看 | 怎么看 | 回答什么 |
|---|---|---|
| **版本** | `node -v`、`git --version`、`python3 --version` | 工具装了吗？版本对吗？ |
| **位置** | `which node`（Windows 用 `where node`） | 终端实际用的是哪一个？ |
| **日志与报错原文** | 终端输出、预览窗格的服务日志 | 到底说了什么？ |

作者环境的真实输出（2026-10-26，macOS）：

```text
Python 3.10.13
/Users/milin/.pyenv/shims/python3
/Users/milin/.nvm/versions/node/v22.21.1/bin/node
/usr/bin/git
```

这里就有两个值得注意的细节：`python3` 来自 `pyenv`，`node` 来自 `nvm`——它们都是**版本管理器**，用哪个版本取决于当前终端的配置。**换一个终端窗口，版本可能不同。** 这是“我这里能跑，Desktop 的终端里不行”的常见来源。

> 本书的 `package.json` 声明了 `"engines": {"node": ">=22"}`，所以 VitePress 站点需要 Node 22 或更高。检查：`node -v`。

## 3. 真实故障一：命令找不到

症状：终端提示命令不存在。作者实测：

```text
zsh: command not found: nonexistent_cmd_xyz
```

（这里故意输入了不存在的命令。你的真实报错通常是 `command not found: node` 之类。）

**分层思考：**

- 工具没装？→ 安装；
- 工具装了，但**不在这个终端的 PATH 里**？→ 这是最常见的。`PATH` 是系统用来查找命令的目录列表；
- 版本管理器没激活？→ 例如 `nvm use 22`。

**最便宜的检查：** `which 命令名`。输出为空 → 终端找不到；输出了路径 → 找到了，问题在别处。

**请 Claude 帮忙时的提示：**

> 终端提示 `command not found: node`。请只做诊断，不要安装任何东西，也不要修改我的配置文件：①运行 `which node`、`echo $PATH`；②告诉我 Node 是否安装在某处；③列出可能的原因，由我决定下一步。

## 4. 真实故障二：端口被占用

作者在写本书的过程中真的遇到了：配置了常用端口后，预览服务启动失败，提示该端口已被占用。再现它：

```sh
python3 -m http.server 48130 --bind 127.0.0.1 &
python3 -m http.server 48130 --bind 127.0.0.1
```

第二个命令的真实输出末尾：

```text
OSError: [Errno 48] Address already in use
```

**怎么办：**

1. 看是谁占的（**只看，不停止**）：

   ```sh
   lsof -nP -iTCP:48130 -sTCP:LISTEN
   ```

   作者实测输出的第二行类似 `python3.1 55233 milin ... TCP 127.0.0.1:48130 (LISTEN)`——能看到进程名与 PID。
2. **判断它是不是你的**。作者发现 8765、8791 这些端口已被**别的项目**的服务占用——那不是本书的进程，**不应该停止它们**。
3. 换一个空闲的大端口号，同时改 `.claude/launch.json` 的 `runtimeArgs` 与 `port` 两处。

> **不要让 Claude 为了“腾出端口”杀进程**，除非你确认那是它自己启动的。杀掉别人的开发服务器，可能中断你的其他工作。Manual 模式下，遇到 `kill`、`pkill` 这类命令，**停下来读清楚再批准**。

清理你自己启动的服务：在启动它的终端按 `Ctrl+C`；若是后台运行的，用 `lsof` 确认 PID 是你的后再结束。

## 5. 预览窗格打不开

按顺序检查：

1. **服务器启动了吗？** Browser 窗格头部的 **Dev servers** 菜单看状态；
2. **端口对吗？** `launch.json` 里的 `port` 与服务实际监听的端口一致吗；
3. **服务的根目录对吗？** 如果服务根目录是别的文件夹，访问 `/` 可能得到列表页或 404；
4. **`runtimeExecutable` 在 PATH 里吗？** Windows 上 `python3` 可能要写成 `python` 或 `py`；
5. **你在 SSH 会话吗？** 官方说明 SSH 会话里 Claude 不能使用 Browser 窗格的工具。

## 6. 工具连接故障（MCP、Connectors）

“某个工具没有连上”，在第 26 章会系统讲。本章只给判断原则：

- **没连上 ≠ 工具坏了。** 先分清：没授权、没配置、网络不通、被组织策略禁止；
- **让 Claude 报告它实际看到的工具列表**，而不是你以为的：

  > 请列出你当前可用的外部工具（名称即可），并说明是否有你期望但缺失的。不要尝试安装或连接任何东西。

- **缺失就是缺失。** 不要让 Claude “模拟”一个工具的结果。如果它在没有连接的情况下给出了“来自某服务的数据”，那是编造，要求它指出数据来源。

Connectors 在官方 Desktop 里于 **Settings > Connectors** 管理（官方参考，2026-10-26）；具体可用性取决于你的计划和组织。

## 7. 失败分支：Claude 开始“修环境”

信号：它提议 `brew install`、`npm install -g`、修改 `~/.zshrc`、`sudo`。

处理：

1. **拒绝**这些命令；
2. 发送：

   > 请先停下。环境修改会影响我整台电脑。请只告诉我：缺什么、为什么、有哪几种解决方式及各自影响，我来决定。

3. 如果确实需要安装，**你自己**在终端执行，并保留记录（版本号）。

## 8. 独立练习

1. 故意把 `launch.json` 的 `port` 改成与 `runtimeArgs` 里不一致的值，观察 Desktop 的行为，并写下你看到的现象（作者未实测）；
2. 在一个新终端窗口运行 `node -v`、`which node`、`echo $PATH`，再在 Desktop 的集成终端里运行同样的三条，比较是否相同。

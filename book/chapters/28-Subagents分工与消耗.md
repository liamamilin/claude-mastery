# 第 28 章｜Subagents、分工与消耗

> 本章终点：你能判断一项任务**该不该交给子代理**；你读懂一份子代理定义；你设计并执行一次“子代理 vs 主会话”的对比，用**自己记录的数据**而不是印象来判断收益与消耗。

## 1. 子代理是什么

官方子代理文档（2026-10-26）：

- 子代理在**自己的上下文窗口**里运行，有自己的系统提示和工具权限；
- 它**看不到你的对话历史**，只收到委派时的那条消息，加上 CLAUDE.md、git 状态和预加载的 skills；
- **只有最终总结回到主会话**，所以冗长的测试日志、搜索结果可以留在外面；
- 它们的请求**计入你同一份使用额度**，每个子代理在运行时消耗自己的令牌。

换句话说：子代理用**更多的总消耗**，换来**更干净的主上下文**和**权限隔离**。是否值得，取决于任务。

### 内置的子代理

官方列出的内置子代理包括：**Explore**（快速、只读，用于搜索与分析代码）、**Plan**（只读调研，用于 Plan 模式）、**general-purpose**（完整工具，用于需要探索加修改的多步任务）。你不需要自己定义也能使用它们——Claude 会按任务特征决定是否委派，你也可以在提示里明确说“用子代理调查……”。

## 2. 值得与不值得

官方给出的判断：

| 用主会话 | 用子代理 |
|---|---|
| 需要来回迭代 | 输出**很冗长**，你不需要它留在主上下文 |
| 各阶段共享大量上下文 | 想**限制工具权限** |
| 快速、有针对性的小改动 | 任务**自成一体**，只需返回摘要 |
| 延迟重要 | |

加上本书的体会：

- **不要把调查与实现的衔接拆开。** 子代理看不到你的对话，所以“它调查完，你再把结论复述给主会话”会丢信息；
- **独立审阅**特别适合子代理：新鲜上下文，没有“刚写完所以偏袒”的问题（第 19 章）；
- **并行不等于更快抵达。** 每个子代理都吃额度，且你要审阅它们所有的输出。

## 3. 一份子代理定义长什么样

资料包 `cases/lab-e-extensions/agents/issue-board-reviewer.md`：

```markdown
---
name: issue-board-reviewer
description: 只读审阅 IssueBoard（Lab B）的改动是否破坏旧功能。在用户要求审阅 diff、或改动涉及 board.js / main.js 后使用。
tools: Read, Grep, Glob
model: haiku
---

你是一名只读的代码审阅者……（正文：检查项、报告方式、不修改任何文件）
```

按官方文档：**只有 `name` 与 `description` 是必需的**；`tools` 是允许使用的工具列表（这里只给了读、搜索、列文件，**没有编辑和运行命令**，这是权限隔离的核心）；`model` 可选 `sonnet`、`opus`、`haiku`、`fable`、完整模型 ID 或 `inherit`——把简单工作路由到较小的模型，官方说可以降低成本；字段名**区分大小写**，写错的字段会被**静默忽略**。

放在 `.claude/agents/`（项目）或 `~/.claude/agents/`（所有项目）。官方说明项目与用户目录会被递归扫描，文件变化通常几秒内生效，但**新建 `agents` 目录本身需要重启**。

### description 决定委派

Claude 按任务与各子代理 `description` 的匹配来自动委派。你也可以显式点名，或用 @ 提及。**一个 `description` 写得含糊的子代理，要么从不被用到，要么被乱用。**

## 4. 动手：一次诚实的对比实验

**目的：** 不凭感觉，记录数据。

### 准备

- 项目：`lab-b`（带第 12 章做到一半的“优先级过滤”，或者任何有改动的状态；至少要有一份有内容的 `git diff`）；
- 把 `issue-board-reviewer.md` 复制到 `lab-b/.claude/agents/`；
- 用 `git diff > change.diff` 之类（别提交这个文件）记下被审阅的改动，保证两边审的是同一份。

### 两个条件，各新开一个会话

**A. 主会话直接审阅：**

> 请审阅当前 `git diff`：旧任务（无 priority）处理是否一致、`main.js` 加载失败时提示是否会被覆盖、有没有超出任务范围。只读，不改文件。每条发现给出触发它的输入，给不出就标“推测”。

**B. 委派子代理：**

> 请使用 `issue-board-reviewer` 子代理审阅当前改动，并把它的发现原样转给我。

### 记录表

| 项目 | A 主会话 | B 子代理 |
|---|---|---|
| 完成用时（大致） | | |
| 使用量（Desktop 的使用量显示，或官方 `/context` 之类的上下文信息） | | |
| 发现了几条？有几条是**真的**（你核对过） | | |
| 有几条是“推测”或误报 | | |
| 主会话上下文被占用的程度 | | |
| 我整合结果花了多少精力 | | |

**注意：** 作者没有跑这个实验，所以这里没有“标准结论”。已知的预期（来自官方说明）是：B 的总消耗不低于 A，但主上下文更干净；谁发现得更准，取决于模型与提示，**你的数据才是答案**。

## 5. 常见误用

| 误用 | 后果 | 改法 |
|---|---|---|
| 把每个小问题都派给子代理 | 总消耗激增；你被一堆摘要淹没 | 只派“冗长且自成一体”的 |
| 派给子代理的任务没写清楚验收 | 摘要空泛 | 同第 7 章：目标、材料、约束、汇报 |
| 让多个子代理同时改同一批文件 | 互相覆盖 | 它们不是 worktree；要隔离需要 `isolation: worktree`（官方字段）或你自己的 worktree（第 16 章） |
| 只相信子代理的“已验证” | 它的验证和你的验证是两回事 | 对它的关键结论抽查（第 18 章） |

## 6. 失败分支

- **子代理没被调用**：`description` 与你的说法不匹配，或文件放错位置；新建了 `agents` 目录没重启；字段名拼错（被静默忽略）；
- **子代理的输出很空泛**：委派消息缺少材料（它看不到你的对话）；让主会话把关键事实写进委派消息；
- **总是“找出一些问题”**：官方提醒，被要求找缺口的审阅者通常会报告一些，即便工作是合理的。要求它**只报告影响正确性的问题**，并给出触发输入。

## 7. 独立练习

写一份你自己的子代理定义，用于“只读调查陌生仓库的数据流”（第 9 章）。要求：`tools` 只含只读工具；`description` 以用户会说的话为触发；正文里写明“事实 / 推测”标注。然后问：**你会真的用它吗？为什么主会话 + Plan 模式不够？**

## 8. 掌握检查

1. 子代理看得到你的对话历史吗？这对你写委派消息有什么要求？
2. 子代理与 worktree 是一回事吗？
3. 你将用什么数据来判断一次委派是否“值得”？

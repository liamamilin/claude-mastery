# 第 09 章｜接手不知道怎么运行的项目

> 本章终点：面对一个没有说明书的陌生项目，你让 Claude 先做**调查**，得到一份把**事实**和**推测**分开的项目简报，以及一条你亲自跑通的启动命令。动手改代码之前，你已经知道入口、数据来源和一个潜在的边界问题。

## 1. 为什么不能一上来就改

你收到一个文件夹，同事说：“给任务增加优先级过滤就行。”没有 README，没有 `package.json`。

最常见的错误顺序是：让 Claude 直接“加一个过滤”。它可能很快交付，但：

- 你不知道它是不是在**真正运行的那份代码**上改的；
- 你没法验证，因为你自己都不知道怎么把它跑起来；
- 隐藏的边界问题（旧数据缺字段）只有在上线后才暴露。

正确的顺序是 **读 → 运行 → 理解 → 再改**。这一章只做前三步。

## 2. 准备：案例 B（IssueBoard）

资料包里的 `cases/lab-b-issueboard/` 是一个小任务看板：

```text
lab-b-issueboard/
├── index.html
├── src/
│   ├── board.js      ← 纯逻辑
│   └── main.js       ← 界面与数据加载
├── data/issues.json  ← 任务数据
├── README.md         ← 给教师；学员请先不要读
└── test.mjs
```

**请不要先读它的 README**——那是给教师的答案。把整个目录复制成 `lab-b`（只复制，不读），在 Desktop 里新建 Local 会话，文件夹选 `lab-b`，权限模式 **Plan**（或 Manual 并禁止改文件）。

## 3. 要一份“事实简报”

**发送到 [Desktop Code] 的提示框（只读调查）：**

> 我刚接手这个项目，没有任何说明。请只做调查，不要修改任何文件，也不要安装任何东西。请写一份简报，包含：
> 1. **入口**：用户从哪个文件开始？页面怎样加载其余代码？
> 2. **数据**：任务数据放在哪里，页面怎样拿到它？
> 3. **怎样运行**：给出一条我可以执行的命令，并说明为什么需要它。
> 4. **怎样测试**：项目里有没有测试？怎么跑？
> 5. **风险**：如果我要“给任务增加优先级过滤”，哪些现有数据或代码可能是陷阱？
>
> 请把每一条标注为【事实：引用文件与行】或【推测：理由】。

### 为什么要求标注“事实/推测”

Claude 的说明读起来都很自信。强制它标注，是为了逼出**它没有真正读过的部分**。【事实】必须能指到文件，你可以点开核对；【推测】是它的判断，需要你验证。

## 4. 你应该得到什么（以及怎样核对）

作者在写本章时按同样思路自己检查了 Lab B，下面是**可被你独立核对的事实**，不是 Claude 的原话：

| 简报应包含 | 在项目里的依据 | 你怎样核对 |
|---|---|---|
| 入口是 `index.html`，用 `<script type="module" src="src/main.js">` 加载逻辑 | `index.html` 末尾 | 在 Files 窗格打开该文件 |
| 数据在 `data/issues.json`，由 `main.js` 里的 `fetch('data/issues.json')` 读取 | `src/main.js` 的 `load()` | 搜索 `fetch` |
| 需要 http 服务才能运行：因为用了 `fetch` 与 ES 模块 | 同上 | 见下节，亲自运行 |
| 有一个测试脚本 `test.mjs`，可用 `node test.mjs` 运行 | 目录中 | 在终端执行 |
| 风险：有一条任务（id 4）**没有 `priority` 字段** | `data/issues.json` | 在 Files 窗格搜索 `priority`，数一数 |

如果 Claude 的简报漏了最后一项，不必惊讶——“漏掉旧数据缺字段”是真实项目中最常见的盲区。**发现它漏了，才是这一章的练习价值。**

## 5. 亲自把它跑起来

不要只相信简报。**[Desktop Terminal]**（`Ctrl+\``）里，在 `lab-b` 目录执行：

```sh
node test.mjs
```

应看到一行以 `PASS` 开头的输出。这表示纯逻辑部分（分组、未完成计数）通过了基础检查——**它不代表页面能正常显示**。

再启动一个本地静态服务（`python3` 自带，不需要安装）：

```sh
python3 -m http.server 48125 --bind 127.0.0.1
```

> 这一步让终端被服务占用，保持它运行；需要时按 `Ctrl+C` 停止。如果端口已被占用，换一个大数字端口，网址里的端口同步改。

然后在 **[Desktop Browser]** 窗格（或普通浏览器）打开 `http://localhost:48125/`。

作者在 Browser 窗格中实测的结果：页面显示“共 5 个任务，未完成 4 个”，三列分别为“待处理（3）”“进行中（1）”“已完成（1）”。你的页面应当一致。

**如果你直接双击 `index.html`（`file://`）**，多数浏览器会因为安全限制拒绝 `fetch` 本地文件，页面停在“加载中”或显示加载失败。作者没有能在 `file://` 下实测，请你自己试一次、记录看到的现象——这是区分“项目坏了”和“运行方式不对”的好例子。

## 6. 让 Claude 把运行方式写下来

确认命令可用后，把它固定下来，避免下一次又要重新调查：

**发送到 [Desktop Code] 的提示框（允许创建文件）：**

> 请在当前目录创建 `RUNNING.md`，只写三件事：怎样启动（我刚验证过的命令）、怎样运行测试、怎样在浏览器里确认运行正常。不要改其他文件。

这是第 12 章“跨会话续写”的第一块砖。

## 7. 失败分支：简报里有编造的细节

可能出现的状况：简报里写了“项目使用 React”“用 `npm start` 运行”，而项目里根本没有这些。

- 用提示核对：`请指出你说“使用 React”的依据文件和行号。`
- 如果它指不出，要求它删掉这一条并说明它为什么会这样推断。
- 之后的每条陈述，仍要求【事实/推测】标注。

**记住：简报是用来被检验的，不是用来被接受的。**

## 8. 独立练习

1. 不看本章，再复制一份 `lab-b` 作为 `lab-b2`，让 Claude 写简报，但这次**要求它多找一件事**：“项目里有没有任何代码在处理 `status` 之外的字段缺失？”
2. 比较两份简报：哪些事实一致，哪些推测相互矛盾？矛盾处说明哪里需要你自己验证。

## 9. 掌握检查

1. 事实与推测的区别是什么？你怎样检验一条【事实】？
2. `node test.mjs` 通过了，为什么还不能说页面能用？
3. 为什么要把运行命令写进 `RUNNING.md`？

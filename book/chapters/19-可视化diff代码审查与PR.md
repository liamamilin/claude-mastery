# 第 19 章｜可视化 diff、代码审查与 PR

> 本章终点：你能用 Desktop 的 diff 视图逐文件审阅一次改动，用行评论让 Claude 修改；会运行 `/code-review` 并**批判性地**对待它的发现；能说清 PR 是什么、什么时候需要它，以及 Desktop 里与 PR 相关的功能需要哪些前置条件。

## 1. 审阅是你的工作，不是 Claude 的

第 15 章你学会了读 diff。这一章把它系统化：Claude 写的改动，在合并之前需要一次真正的审阅——这是你对结果负责的地方。

官方最佳实践对“审阅”有两个值得吸收的洞见：

1. **让另一个上下文来审。** 在一个干净的上下文里审阅，不会偏袒刚写完的代码——“一个新鲜的上下文会改进代码审查，因为 Claude 不会偏向它刚写的代码”。
2. **别追求零发现。** 官方提醒：被要求“找缺口”的审阅者通常会报告一些问题，哪怕工作本身是合理的；追逐每一条发现会导致过度工程。应当只关注影响正确性或既定要求的缺口，其余当作可选。

## 2. Desktop 的 diff 视图

按官方参考（2026-10-26）：

- 打开：点会话里的 `+12 -1` 之类的行数（在 **Changes** 卡片里），或点标题栏 **Changes**；macOS 快捷键 `Cmd+Shift+D`；
- 逐文件查看；**点击任何一行就可以评论**；
- 用 `Cmd+Enter`（Windows `Ctrl+Enter`）一次性提交所有评论；Claude 读取评论并修改。

### 一个审阅清单

对每一次改动，逐条问：

| 检查 | 问题 |
|---|---|
| 范围 | 改的文件都是任务需要的吗？ |
| 大小 | 行数与任务相称吗？ |
| 意图 | 每一处改动我能不能说出为什么？ |
| 副作用 | 有没有改动存储格式、删除函数、新增依赖？ |
| 测试 | 测试有没有被改动？是增加验证，还是削弱验证？ |
| 遗漏 | 任务要求的每一项都做到了吗？ |
| 敏感信息 | 有没有把密钥、路径、个人信息写进去？ |

最容易被忽略的是“测试有没有被改动”：**悄悄放宽断言来让测试通过**，是需要警惕的模式（第 18 章）。

### 动手：评论式纠偏

用第 15 章的 `lab-a-git`，让 Claude 加一个“按标题搜索”的最小实现（Manual）。打开 diff 后：

1. 找一处你想改的小点（命名、提示文案、一个多余的空行），**点那一行写评论**，例如：“这里的 `q` 改成 `keyword`，让读者一眼看懂”；
2. 再找一处你认为有问题的点（比如它同时改了存储相关代码），评论：“这里与任务无关，请撤销”；
3. `Cmd+Enter` 提交所有评论；
4. 观察 Claude 有没有**只**改你评论的位置。

记录：评论式纠偏用了几条评论？与第 14 章里用大段文字纠偏相比，哪个更省力？

## 3. `/code-review`：让另一个“视角”审一遍

官方说明：在提示框输入 `/code-review`，Claude 会审阅当前变更。在本地、SSH 和 WSL 会话中，发现会显示在一张 **Code review** 卡片里，带有 **Walk through in diff** 与 **Apply fixes** 两个按钮；官方最佳实践也指出，该技能在一个新的子代理里审阅当前 diff 的正确性问题，并把发现返回会话。

### 怎样用它

1. 先自己读一遍 diff，写下你的疑问；
2. 再运行 `/code-review`；
3. **逐条评估每个发现**：它是真问题（会导致错误）、是偏好（风格），还是误报？
4. 只对真问题点 **Apply fixes** 或让 Claude 修；
5. 修复后再看 diff，确认**修复本身**没有越界。

### 一个重要提醒

**不要因为审阅工具说“有问题”就机械修改。** 每个发现都是一个假设，需要你对照代码核实：

> 请指出这条发现对应的具体代码和一个会触发它的输入。

给不出触发输入的发现，很可能是推测。

## 4. PR 是什么

**PR（Pull Request，拉取请求）** 是在 GitHub 等平台上请求把一个分支的改动合并进主分支的提议。它的价值：

- 把改动集中展示给人（和自动检查）审阅；
- 留下“为什么这样改”的记录；
- 合并前可以跑 CI（自动构建和测试）。

**你的练习项目不需要 PR。** 个人项目直接在本地分支合并也完全正常。当你要与别人协作、或想借助 GitHub 的检查和审阅时，才需要它。

### Desktop 里的 PR 相关功能与前置条件

官方参考列出：

- Claude 可以在你点击 **Create PR** 后推送分支并运行 `gh pr create`（至少在 SSH 会话中有明确描述）；
- PR 的 **⋮** 菜单提供 **Auto-fix**（Claude 处理失败的检查和新的审阅评论）与 **Merge when ready**（开启 GitHub 自动合并；Desktop 默认请求 squash 合并，除非基础分支使用合并队列；SSH 与 WSL 会话中不可用）；
- **这些都依赖 GitHub CLI（`gh`）和 GitHub 登录。**

> **本书的立场：** 推送到远程、创建 PR、开启自动合并都是**对外可见的动作**。除非你自己明确决定，不要让 Claude 去做。把它们当作需要你批准的发布步骤，而不是日常修改的一部分。

## 5. 把改动整理成一个好审阅的单元

好的 PR（或好的提交）：

| 特征 | 理由 |
|---|---|
| 一个目的 | 评审的人只需要回答一个问题 |
| 小 | 越大越难看出问题 |
| 描述“为什么” | 代码能看出“是什么” |
| 附验证证据 | “我做了什么检查，结果如何”，包括没覆盖的部分 |

让 Claude 起草说明时，给它一个格式：

> 请为这次改动写一份变更说明（中文），包含：目的；改了哪些文件；我怎样验证过（具体步骤与结果）；没有验证的部分；风险。只写事实，不夸大。

**然后你来核对**：每一条“验证过”，你是否真的看到证据？

## 6. 失败分支：审阅被淹没

diff 太大，你读不下去，开始“差不多就行”。

- **拆**：让 Claude 把变更拆成几个独立的提交或分支，分别审；
- **回退到更小的范围**（第 24 章）；
- **用更多的检查替代你的眼睛**：测试与浏览器检查（第 17、18 章）；
- 承认：**你审不了的改动，不应该被合并。**

## 7. 独立练习

拿第 15 章中任一次 Claude 的改动，先自己写 5 条审阅意见（含至少一条“没问题的确认”）；再运行 `/code-review`；比较两份意见：哪些重合？它发现了你没发现的什么？你发现了它没发现的什么？

## 8. 掌握检查

1. 为什么在“新的上下文”里做审阅更可靠？
2. `/code-review` 的发现为什么不能全部照单执行？
3. 哪些 PR 相关操作属于“对外可见”，需要你亲自决定？

# 第 22 章｜停止反复补丁：当“再修一次”不再有用

> 本章终点：面对连续修复失败，你能够从“继续修改表面症状”转为“提出能被证据检验的假设”，找到问题真正发生的位置，再做最小改动与回归测试。

## 1. 故障：删除之后，刷新又回来了

一个本地收藏工具出现这样的现象：

1. 点击某条收藏的“删除”按钮，条目立即从列表中消失。
2. 刷新浏览器，刚才的收藏再次出现。
3. Claude 已经改过按钮的事件绑定与样式，症状仍然存在。

这很容易让人困惑：点击时确实起作用了，为什么刷新后又回来？

本章配有一个独立的故障实验：`cases/lab-d-persistence/`。这个练习程序**故意在删除路径漏掉持久化保存**，不是一份需要在教材编写阶段“顺手修掉”的坏代码。

## 2. 为什么继续修改按钮通常没用？

我们的观察是：“点击删除，界面消失；刷新后恢复。”这个现象至少包含两个不同的时间点：

- **当前页面中的状态**：可能只存在于 JavaScript 运行内存。
- **刷新后重新读取的状态**：可能来自浏览器 `localStorage`、远程数据库或其他持久化来源。

如果界面已经删除成功，那么“点击按钮完全无效”的解释就与观察不一致。更值得问的是：**删除后的新状态有没有写进持久化存储？**

下面是这种问题的最小关系图：

```text
点击删除
   ↓
移除内存中的对象 ─────→ 立即重绘页面（看起来删除成功）
   │
   └── [可能漏掉] 写回 localStorage
                            ↑
                        刷新时重新读取
```

这不是说所有“刷新恢复”都一定是 `localStorage`；它只说明**我们应该优先检查刷新时的数据来源**。这个检查可以把多个猜测分开。

## 3. 先复现，不急着修改

### 步骤 A｜打开故障案例

**[系统文件管理器 / 浏览器]** 在已解压的资料包里找到 `cases/lab-d-persistence/index.html`，使用浏览器打开。如果你的浏览器限制 `file://` 上的持久化存储，可在该目录启动本地静态服务，再用 `http://localhost:...` 打开，确保前后测试使用同一个来源地址。

观察：页面中已有或可以新增一个任务。点击删除，它从屏幕消失；刷新页面，它有可能重新出现。在正式修改前记录浏览器、地址、操作顺序。若你的环境无法重现，应先确认本地存储是否被实际使用，以及测试前是否添加了任务。

## 4. 看数据流，找到最小判别检查

代码中有两个关键动作：

**保存数据（示意，实际请读源码）**：

```js
function persist() {
  localStorage.setItem('mastery_tasks', JSON.stringify(tasks));
}
```

**删除任务后更新屏幕（练习版的关键缺失）**：

```js
function removeTask(id) {
  tasks = tasks.filter(task => task.id !== id);
  render();
  // 没有调用 persist()，所以刷新重新读取到了旧数据
}
```

这里的源代码显式地显示：删除后只改动了运行中的 `tasks`，没有写回存储。刷新会触发脚本重新读取本地持久化副本，于是条目出现。这条**能够解释完整现象的因果链**，比“再写一版按钮”更有价值。

当然，真正的项目里代码可能不这么简单：持久化操作可能在 React state effect、数据库事务、网络请求或后台同步里。遇到不同实现时，应找它实际保存与加载的位置，而不是强迫使用本教材的局部例子。

## 5. 只做必要的修复

你可以给 Claude 的下一条任务：

> 我们已经确认：删除只改了内存并重绘，刷新重新读取了旧的 localStorage。请仅修复删除后缺失的持久化写入，不重构无关 UI。修复后描述变更范围，并通过“新增→刷新→删除→刷新”完整检查；如果某一步无法自动运行，就明确留给我手动验收。

在这个教学缺陷里，修复通常只需要调用 `persist()`：

```js
function removeTask(id) {
  tasks = tasks.filter(task => task.id !== id);
  persist();
  render();
}
```

这段代码解释的是**修复方向**。更重要的是把故障背后的事实过程说清楚。除了“修复后删除有效”，你还应检查**新增后的记录刷新仍存在**，确保修复没有破坏另一条写入路径。

## 6. 完成一次闭环验证

| 检查动作 | 期望行为 | 如果不符，接下来查什么 |
|---|---|---|
| 新增“研究资料 A” | 列表出现 A | 输入事件和重绘路径 |
| 刷新 | A 依然存在 | 保存路径、浏览器存储策略 |
| 删除 A | A 从列表消失 | 点击事件和列表状态 |
| 再次刷新 | A **不会**回来 | `localStorage` 是否已删除写回 |
| 再新增 B | B 正常保存 | 回归确认写入功能没有被破坏 |

只“刷新前不出现”不算修复完成；那正是故障本身。

## 7. 这个经验如何迁移？

同样的问题可能换成其他形式：

- 页面上状态是“已发送”，服务端其实没有保存。
- 表格里数字显示更新，但导出时仍是旧值。
- Claude 报告测试通过，但运行用的是另一份旧构建文件。
- 两个 Git worktree 的代码彼此独立，读者查看了错误的工作目录。

这里有共同点：**你观察到的是哪一层状态？下一个阶段究竟从哪里取值？**

当修补多次无效时，优先问：我们有没有反复修改同一个未被证实的假设？是否存在一个更小的实验能直接排除它？

## 9. 自测：你真的能够接管失败吗？

1. 为什么“点击消失”不能证明“删除已经永久成功”？
2. 如果你检查过 `persist()` 被调用，但刷新仍恢复，你会再检查哪种不同假设？
3. 如果另一个问题的症状是“按钮完全不响应”，你还会优先查持久化吗？为什么？

**本章要记住的不是 localStorage，而是方法：复现 → 事实 → 假设 → 最小判别实验 → 最小修复 → 回归检查。**

# 第 21 章｜先判断问题发生在哪一层

> 本章终点：面对一个症状，你能先列出它**可能发生在哪几层**，为每一层写出一条**可以检验的假设**，再选一个能一次排除最多层的检查。你会用本书已经出现过的真实故障练习这件事。

## 1. 同一个症状，不同的病因

“页面上看不到数据”可能是：

- 数据文件根本没取到；
- 取到了但格式坏了；
- 格式对，页面渲染出错；
- 渲染对，被过滤条件隐藏；
- 一切都对，你打开的是**另一个目录里的旧页面**。

如果你不分层就开始改，很可能在**错误的层**上反复用力——这就是第 22 章要处理的“反复补丁”的来源。本章先给你一张分层的地图。

## 2. 八层地图

![故障分层：从需求到测试方法，八层都可能产生相似症状。越靠上的层越容易被忽略。](/figures/fault-layers.svg)

| 层 | 典型问题 | 在本书里见过的例子 |
|---|---|---|
| **1 需求** | 目标没说清，Claude 做对了“另一件事” | 第 5 章“更方便收藏资料” |
| **2 环境** | 运行方式不对、端口占用、工具缺失 | 第 9 章 Lab B 需要 http 服务；端口被其他项目占用 |
| **3 权限** | 某个操作被拒绝或需要批准 | 第 13 章 Manual 与 Accept edits |
| **4 依赖/工具** | 版本不对、命令不存在、连接未建立 | 第 23 章 |
| **5 实现** | 代码逻辑本身错误 | Lab C 固定列宽（第 17 章） |
| **6 状态与数据** | 内存、存储、文件里的数据不一致或格式坏 | Lab D 删除不保存；Lab B 数据尾逗号 |
| **7 呈现** | 对数据的显示方式有问题 | 错误提示被覆盖（第 10 章） |
| **8 测试方法** | 检查没有覆盖到真实问题 | 第 18 章“测试通过但页面坏” |

这不是官方分类，是本书为训练判断力整理的一个**工作用的框架**。层与层之间会重叠，用它来**列出选项**，而不是给出答案。

## 3. 一个三步法

### 步骤 1：只记录现象，不下结论

写成“动作 → 实际结果 → 期望结果”：

> 点击“删除” → 任务从列表消失，刷新后又出现 → 刷新后不应出现。

**不要写“删除功能坏了”。** 那是结论，且已经预设了位置。

### 步骤 2：每层一条假设

针对这个现象，不同层的假设：

| 层 | 假设 | 一个能检验它的最小检查 |
|---|---|---|
| 实现 | 点击事件没有绑定 | 点击后列表是否变化（**已变化 → 排除**） |
| 状态/数据 | 删除只改了内存，没改存储 | 点击前后查看 `localStorage` 的值 |
| 环境 | 刷新载入了另一份旧文件 | 看页面脚本的真实 URL 与修改时间 |
| 测试方法 | 我以为刷新了，其实没刷新 | 在控制台打印页面加载时间 |

**关键：选一个能同时排除多个假设的检查。** 第一条被“列表已经变化”这件事免费排除了——这种“已有的现象本身就是证据”要先用起来。

### 步骤 3：从最便宜、区分力最强的开始

便宜（几秒钟）、区分力强（结果能排除很多假设）的检查优先。例如“点击前后看 `localStorage`”，比“重写删除逻辑”便宜得多，也有力得多。

## 4. 动手：用 Lab B 的三个症状做分层练习

用第 10 章你已有的 `lab-b3`（trailing-comma 数据）与正常数据，**先不要让 Claude 回答**，自己填表：

| 症状 | 现象（动作→结果→期望） | 至少两层的假设 | 最便宜的检查 |
|---|---|---|---|
| A 双击 `index.html` 页面“加载中”不变（你自己试一次） | | | |
| B 页面“共 0 个任务”，没有提示 | | | |
| C 控制台出现 `SyntaxError` | | | |

作者对 B 的参考答案（你的可以不同）：

- 现象：打开页面 → 显示“共 0 个任务”，无提示 → 期望显示 5 个任务；
- 假设：①数据请求失败（环境/数据）；②请求成功但内容读不出（数据）；③读出了但被过滤（实现）；
- 最便宜的检查：网络面板看 `data/issues.json` 的状态码。作者实测为 `200 OK`——**排除①**；再在控制台解析，得到 `SyntaxError`——**证实②**。

填完后，再让 Claude 做同一件事（Plan 模式），对比它的分层与你的有什么不同。

## 5. 让 Claude 帮你分层

**发送到 [Desktop Code] 的提示框（只读）：**

> 症状：（动作 → 实际 → 期望）。请不要修改任何文件，也不要给出修复。请：
> 1. 列出这个症状可能发生的 4 个以上不同层（需求/环境/权限/依赖/实现/状态/呈现/测试方法）；
> 2. 每层给出一条可检验的假设；
> 3. 指出哪一个检查最便宜、能一次排除最多假设，并说明我该怎样做这个检查；
> 4. 标注哪些你已经从文件里确认，哪些只是推测。

这个提示的核心是：**要它列选项和检验方式，而不是给答案。**

## 6. 失败分支：分层本身分错了

你可能把“环境”问题当成“实现”问题，反之亦然。信号：**你做的检查没有改变任何假设的可信度。** 如果一个检查的结果既不支持也不排除任何假设，说明它区分力不足，换一个。

## 7. 独立练习

给下列症状各写一个“动作 → 结果 → 期望”，并列出至少三层的假设：

1. Claude 说测试全部通过，但你在浏览器里点击按钮没有反应；
2. 预览窗格显示的页面与你刚刚修改的内容不一致；
3. Claude 说“已经创建了文件”，但文件管理器里找不到。

## 8. 掌握检查

1. 为什么记录现象时不应写“某某功能坏了”？
2. “已有的现象本身就是证据”的例子是什么？
3. 什么样的检查“区分力强”？
